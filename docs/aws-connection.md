## 1. Architecture Overview

There are two AWS accounts involved in every connection:

| Account | Description |
|---|---|
| **Infra Genie Account** (`AWS_INFRAGENIE_ACCOUNT_ID`) | Where the Infra Genie backend runs. Has its own IAM credentials used to call STS. |
| **Customer Account** | The user's own AWS account. Infra Genie never has direct long-term credentials for it. |

```
Infra Genie Backend (Account A)
        │
        │  sts:AssumeRole
        │  + ExternalId
        ▼
Customer AWS Account (Account B)
        │
        └── InfraGenieExecutionRole
                │
                ├── Trust Policy: only Account A may assume, with ExternalId
                └── Permission: AdministratorAccess (TESTING ONLY)
```

Infra Genie **never asks for**:
- AWS root credentials
- IAM username / password
- Permanent AWS Access Key ID or Secret Access Key

Instead, it uses **AWS STS AssumeRole** to get short-lived (15-minute) temporary
credentials on demand.

---

## 2. Why Cross-Account IAM Role?

### Alternatives considered and rejected

| Method | Problem |
|---|---|
| Root credentials | Full account takeover risk; impossible to scope; AWS explicitly forbids sharing |
| IAM user access keys | Permanent credentials; rotate manually; high blast radius if leaked |
| Federated SAML | Complex setup for customers; requires IdP configuration |
| Cross-account role + STS | ✅ AWS-native pattern; temporary creds; auditable; revocable |

### Cross-account role benefits

- **No permanent credentials stored** — Infra Genie holds zero long-lived secrets for
  customer accounts.
- **Customer stays in control** — the customer creates the role themselves via
  CloudFormation. They can delete the stack at any time to immediately revoke all
  access.
- **Auditable** — every AssumeRole call appears in the customer's CloudTrail.
- **Scoped** — the trust policy restricts assumption to the Infra Genie account only.
- **Revocable** — deleting the CFN stack immediately revokes access. No credentials
  to rotate.

## 3. External ID

The External ID is a cryptographically random UUID v4 generated by Infra Genie when a
new connection is started.

```
Example: 4b8f9e41-6f5a-4c77-8f7e-2f3b9c9c1e12
```

### What it prevents — the Confused Deputy attack

Without an External ID, any AWS customer could create a role that trusts
Infra Genie's account. If Infra Genie were ever tricked into assuming a role in the
wrong account (e.g., by a malicious user submitting an ARN that belongs to
another customer's account), it would have unintended access.

The External ID prevents this:

```json
"Condition": {
    "StringEquals": {
        "sts:ExternalId": "4b8f9e41-6f5a-4c77-8f7e-2f3b9c9c1e12"
    }
}
```

Infra Genie only calls AssumeRole with the External ID it generated and stored for
that specific connection. An attacker cannot reuse Infra Genie's identity to assume
a role in an account they don't own.

### External ID rules

- Generated with `uuid.uuid4()` — cryptographically random, 122 bits of entropy.
- Unique per connection — never reused between customers.
- Not derived from the AWS Account ID.
- Not hardcoded in source code.
- Stored in `cloud_accounts.external_id`.
- Returned to the frontend **only once** (at connection setup time, so the user
  can embed it in CloudFormation). Never included in list/detail API responses.

## 4. CloudFormation Setup

Infra Genie generates a parameterised CloudFormation template (JSON) that the
customer deploys in their own AWS account.

### Parameters

| Parameter | Description |
|---|---|
| `InfraGenieAccountId` | Infra Genie's AWS Account ID — pre-filled |
| `ExternalId` | The unique External ID — pre-filled |
| `RoleName` | Defaults to `InfraGenieExecutionRole` |

### What the stack creates

A single IAM role: `InfraGenieExecutionRole`

**Trust policy** (conceptual):
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::<INFRAGENIE_ACCOUNT_ID>:root"
    },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": {
        "sts:ExternalId": "<EXTERNAL_ID>"
      }
    }
  }]
}
```

The Principal is **never** `"*"`. Only the Infra Genie AWS account can assume the role.

### How to deploy

1. Download the CFN template from the Infra Genie UI (Cloud Accounts → Connect → Step 1).
2. Open the AWS CloudFormation console in your account.
3. Create stack → With new resources → Upload a template file.
4. Upload the downloaded JSON.
5. Accept the default parameter values (they include your External ID).
6. Create stack. Wait for `CREATE_COMPLETE`.
7. Copy the `RoleArn` from the stack Outputs tab.
8. Return to Infra Genie, paste the Role ARN, click Verify Connection.

### Stack name convention

`InfraGenie-CrossAccount-<account_id>`

## 5. STS AssumeRole

After the customer provides their Role ARN, Infra Genie calls AWS STS:

```python
sts_client = boto3.client("sts", region_name=settings.aws_default_region)

response = sts_client.assume_role(
    RoleArn="arn:aws:iam::222222222222:role/InfraGenieExecutionRole",
    RoleSessionName="InfraGenieSession-<connection_id_prefix>",
    ExternalId="4b8f9e41-6f5a-4c77-8f7e-2f3b9c9c1e12",
    DurationSeconds=900,  # 15 minutes — minimum
)
```

The `RoleSessionName` is unique per connection (includes connection ID prefix) so
CloudTrail entries are easy to attribute.

On success, AWS returns temporary credentials:

```json
{
  "Credentials": {
    "AccessKeyId":     "ASIA...",
    "SecretAccessKey": "...",
    "SessionToken":    "...",
    "Expiration":      "2026-09-27T17:00:00Z"
  }
}
```

These are loaded into an in-memory `boto3.Session` and used immediately.

## 6. Temporary Credentials

### In-memory only

Temporary credentials from STS AssumeRole are **never**:
- Written to the database
- Written to log files
- Returned in any API response
- Sent to the frontend

They exist only in the FastAPI process memory for the duration of the
verification request (typically < 2 seconds).

### Lifecycle

```
AssumeRole called
      │
      ▼
boto3.Session created with temporary credentials
      │
      ▼
GetCallerIdentity called (verify account ID)
      │
      ▼
EC2 DescribeRegions called (verify API access)
      │
      ▼
Session object garbage-collected
Credentials no longer exist anywhere
```

### Duration

15 minutes (`DurationSeconds=900`) — the minimum AWS allows. This is intentional:
the credentials are only needed for verification, so minimising their lifetime
reduces risk if a credential somehow leaked.

## 7. Connection Verification

After AssumeRole, Infra Genie performs two harmless read-only checks:

### Check 1 — STS GetCallerIdentity

```python
identity = sts_client.get_caller_identity()
# Returns: { "Account": "222222222222", "UserId": "...", "Arn": "arn:aws:sts::..." }
```

Infra Genie verifies that `identity["Account"]` matches the AWS Account ID the user
originally entered. This guards against a user providing a Role ARN from a
different account than the one they registered.

### Check 2 — EC2 DescribeRegions

```python
ec2 = session.client("ec2", region_name=customer_region)
regions = ec2.describe_regions(AllRegions=False)
```

A safe, read-only EC2 call that confirms the temporary credentials can reach the
AWS API and that the target region is accessible.

### What is NOT done during verification

- No EC2 instances created
- No VPCs created
- No EKS clusters created
- No S3 buckets created
- No IAM modifications
- No CloudFormation stacks created

Verification **only** proves that authentication and basic API access work.

### Status transitions

```
PENDING → VERIFYING → CONNECTED  (success)
                    → FAILED      (any error)
```

## 8. Testing — AdministratorAccess

> ⚠️ This section describes a deliberate decision for the prototype phase.

The CloudFormation template attaches the AWS managed policy
`arn:aws:iam::aws:policy/AdministratorAccess` to `InfraGenieExecutionRole`.

**Why:**  
During the prototype/testing phase, using AdministratorAccess ensures the
complete deployment workflow can be validated end-to-end without any
permission-related failures interrupting development.

**This is intentional and temporary.**

It is clearly documented in:
- The CloudFormation template description
- The template's `PermissionNote` tag
- The `ManagedPolicyArns` comment in `aws_connection.py`
- The wizard UI (amber notice box)

### How to identify in the template

Search for `"TESTING ONLY"` in the generated CloudFormation JSON:

```json
"ManagedPolicyArns": [
    "arn:aws:iam::aws:policy/AdministratorAccess"
    // TESTING ONLY ↑ — replace with least-privilege ARN in production
]
```

## 9. Security Considerations

### What Infra Genie never does

| ❌ Never | Why |
|---|---|
| Ask for root credentials | Not needed; would be catastrophic if leaked |
| Ask for permanent access keys | Temporary credentials are safer |
| Store temporary credentials | No reason to persist short-lived secrets |
| Log SecretAccessKey or SessionToken | These appear nowhere in logs |
| Return credentials to the frontend | Frontend only receives metadata |
| Allow `Principal: "*"` in trust policy | Would allow any AWS account to assume the role |

### Multi-tenant isolation

Every database query that touches `cloud_accounts` is scoped by `user_id`:

```python
select(CloudAccount).where(
    CloudAccount.id == connection_id,
    CloudAccount.user_id == current_user.id,  # ← always enforced
)
```

User A cannot read, verify, or disconnect User B's AWS accounts even if they
guess a valid `connection_id`.

### External ID confidentiality

The External ID is shown in the UI once (step 1 of the wizard) so the user can
copy it into CloudFormation. After that:
- It is stored in `cloud_accounts.external_id` (server-side only).
- It is never returned in `GET /api/cloud/aws` (list endpoint).
- It is never returned in verify or disconnect responses.

### Audit logging

Every meaningful event is logged with structured metadata:

| Event | Log level |
|---|---|
| Connection created | INFO |
| CFN template generated | INFO |
| AssumeRole attempted | INFO |
| AssumeRole succeeded | INFO |
| AssumeRole failed | WARNING |
| Identity verified | INFO |
| Verification failed | WARNING |
| Account disconnected | INFO |

Logs never contain `SecretAccessKey`, `SessionToken`, or full `AccessKeyId`
(only a 4-character masked prefix is logged for correlation).

## 10. Production Migration — Least Privilege

The current `AdministratorAccess` policy will be replaced with a custom
least-privilege policy after the complete deployment workflow is tested.

### Migration steps

1. Complete prototype testing with `AdministratorAccess`.
2. Enable AWS CloudTrail in the test account.
3. Run all Infra Genie operations (analysis, deployment, monitoring, etc.).
4. Use AWS IAM Access Analyzer or the CloudTrail event history to identify every
   IAM action Infra Genie actually calls.
5. Create a custom IAM policy `InfraGenieLeastPrivilegePolicy` containing only
   those actions.
6. Update the CloudFormation template:
   - Remove: `arn:aws:iam::aws:policy/AdministratorAccess`
   - Add: `arn:aws:iam::<INFRAGENIE_ACCOUNT_ID>:policy/InfraGenieLeastPrivilegePolicy`
7. In `aws_connection.py`, update the comment and policy ARN.
8. Test all workflows with the new policy before rolling out to customers.

### Expected production policy actions (preliminary estimate)

```
ec2:Describe*
eks:Describe*, eks:List*
s3:GetObject, s3:PutObject, s3:ListBucket
iam:GetRole, iam:PassRole
cloudformation:Describe*, cloudformation:List*, cloudformation:CreateStack, ...
sts:GetCallerIdentity
logs:CreateLogGroup, logs:PutLogEvents
```

This list will be finalised after the deployment workflow is completely built.

## 11. Troubleshooting

### "AWS role assumption was denied"

**Cause:** The trust policy in the customer's IAM role doesn't allow Infra Genie's
account, or the External ID doesn't match.

**Fix:**
1. Open the customer's AWS console → IAM → Roles → `InfraGenieExecutionRole`.
2. Check the Trust relationships tab.
3. Verify the Principal matches `arn:aws:iam::<INFRAGENIE_ACCOUNT_ID>:root`.
4. Verify the `sts:ExternalId` condition matches the External ID shown in
   Infra Genie (visible in step 1 of the wizard, before you advance to step 2).
5. If the stack was created with wrong parameters, delete the stack and re-create it
   using the fresh template download from Infra Genie.

### "InfraGenieExecutionRole was not found"

**Cause:** The CloudFormation stack hasn't been created yet, or it failed.

**Fix:**
1. Open the customer's CloudFormation console.
2. Check if the stack `InfraGenie-CrossAccount-<account_id>` exists.
3. If `CREATE_FAILED`, check the Events tab for the error and re-create.
4. If the stack doesn't exist, go back to step 1 in the Infra Genie wizard.

### "AWS account ID does not match"

**Cause:** The Role ARN pasted in step 2 contains a different account ID than
the one entered in step 1.

**Fix:** Verify you're logged into the correct AWS account in both the
CloudFormation console and the Infra Genie wizard.

### "Infra Genie backend has no AWS credentials configured"

**Cause:** The Infra Genie backend itself doesn't have credentials to call STS.

**Fix (local dev):** Set `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` in
`.env` for the Infra Genie backend IAM user (must have `sts:AssumeRole` permission).

**Fix (production):** Attach an IAM role with `sts:AssumeRole` to the EC2
instance / ECS task running the Infra Genie backend. Remove the access key env vars.

### "Temporary credentials expired"

**Cause:** The 15-minute STS session expired before verification completed.
This is very unlikely in normal operation.

**Fix:** Click "Verify Again" — a fresh AssumeRole call will be made.

## 12. API Reference

### POST /api/cloud/aws/connect

Start a new AWS account connection. Returns the External ID and CloudFormation template.

**Request:**
```json
{
  "account_id": "222222222222",
  "region": "ap-south-1"
}
```

**Response (201):**
```json
{
  "connection_id": "a1b2c3d4-...",
  "provider": "AWS",
  "account_id": "222222222222",
  "region": "ap-south-1",
  "external_id": "4b8f9e41-6f5a-4c77-8f7e-2f3b9c9c1e12",
  "role_name": "InfraGenieExecutionRole",
  "status": "PENDING",
  "INFRAGENIE_ACCOUNT_ID": "111111111111",
  "cloudformation_template": { ... }
}
```

---

### POST /api/cloud/aws/{connection_id}/verify

Provide the Role ARN and trigger STS verification.

**Request:**
```json
{
  "role_arn": "arn:aws:iam::222222222222:role/InfraGenieExecutionRole"
}
```

**Success response (200):**
```json
{
  "status": "CONNECTED",
  "account_id": "222222222222",
  "region": "ap-south-1",
  "role_arn": "arn:aws:iam::222222222222:role/InfraGenieExecutionRole",
  "last_verified_at": "2026-09-27T16:30:00Z",
  "message": "AWS account connected successfully."
}
```

**Failure response (403/401/404):**
```json
{
  "status": "FAILED",
  "error_code": "AccessDenied",
  "message": "AWS role assumption was denied. Verify the IAM trust policy..."
}
```

---

### GET /api/cloud/aws

List all AWS accounts for the authenticated user. Never returns credentials or External ID.

**Response (200):**
```json
[
  {
    "id": "a1b2c3d4-...",
    "provider": "AWS",
    "account_id": "222222222222",
    "role_arn": "arn:aws:iam::222222222222:role/InfraGenieExecutionRole",
    "region": "ap-south-1",
    "status": "CONNECTED",
    "connection_error": null,
    "created_at": "2026-09-27T14:00:00Z",
    "updated_at": "2026-09-27T14:05:00Z",
    "last_verified_at": "2026-09-27T16:30:00Z"
  }
]
```

---

### DELETE /api/cloud/aws/{connection_id}

Soft-disconnect. Marks the record `DISCONNECTED` in Infra Genie's database.
Does NOT delete the IAM role from the customer's AWS account.

**Response (200):**
```json
{
  "status": "DISCONNECTED",
  "message": "Connection removed from Infra Genie. To fully revoke access, delete the CloudFormation stack 'InfraGenie-CrossAccount-<account_id>' from your AWS console."
}
```
